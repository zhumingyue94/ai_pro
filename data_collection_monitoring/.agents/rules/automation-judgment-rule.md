# 自动化判定规则

## 1. 定位与适用范围

本规则是测试用例生成阶段和测试用例评审阶段判断自动化候选的唯一标准来源。规则只判断测试用例在设计层面是否适合转化为稳定的自动化测试，不代表：

- 已经编写自动化脚本；
- 当前环境、账号、权限或测试数据已经就绪；
- 已经执行测试；
- UI 执行已经通过；
- 已完成禅道同步。

本规则适用于 UI、接口或可通过机器执行的业务验证用例。人工操作和人工结果仍可作为测试设计内容，但不能因此直接标记为自动化候选。

### 1.1 判定输入边界

判定只允许使用以下输入：

- 需求、需求分析和测试计划中与本用例相关的业务规则、范围与责任边界；
- 用例自身的 `preconditions`、`steps.action` 和 `steps.expected` 所表达的业务语义。

以下内容**不得**作为 `auto` 判定、一票否决、评审门禁、阻塞或任何字段的判断条件，只可作为普通参考资料：

- 页面清单文件（`page.json`、`design.json`、`page_inventory`）是否存在，以及是否登记本用例涉及的页面；
- 是否完成页面采集，以及采集状态（`contract_status`、`capture.status`、`evidence.status`、`not_captured`、`partial`、`blocked`）；
- 定位器证据（`locator_candidates`、`locator_ref`、`state_id`、`page_id`、`capture_id`）；
- 截图、DOM 快照、日志和 trace 等采集产物是否存在。

定位策略与定位器成败不参与本规则判定，由 `07_ui_automation` 依据真实 DOM 独立处理；执行阶段的定位失败记为执行问题，不得回溯改写 `auto`。

## 2. 字段约定

### 2.1 `auto` 字段

`auto` 只能使用以下两个字符串值：

```yaml
auto: "auto"
auto: "no"
```

禁止把以下值写入 `auto` 字段：

```text
true
false
"true"
"false"
yes
manual
partial
blocked
null
```

YAML 中的 `no` 必须以字符串形式写入，避免被解析为布尔值。

### 2.2 判定结论的落点

`auto` 是本规则唯一的判定结论字段，只允许字符串 `auto` 或 `no`。

- `auto=no` 必须在评审记录或 HANDOFF 中说明具体的一票否决原因，不得只写"不可自动化"或"条件不足"；
- 用例 YAML 不再写入 `automation_evaluation` 等评估结构字段；历史产物中已存在的该类字段仅作兼容读取，不得作为新用例生成值，也不得据此推断 `auto`；
- `matched`、`status`、`reason_codes` 等状态说明只出现在评审记录或 HANDOFF 的说明文字中，不作为用例字段。

判定说明中的逻辑状态约定如下：

| 状态 | 含义 | `auto` 取值 |
|---|---|---|
| `matched` | 自动化设计条件已满足 | `auto` |
| `partial` | 设计方向可自动化，但断言或技术证据仍不完整 | `auto` |
| `blocked` | 设计可自动化，但当前环境、账号、权限、数据或执行依赖未就绪 | `auto` |
| `not_suitable` | 设计上存在不可消除的人工、主观或不可控依赖 | `no` |

`partial` 和 `blocked` 只能作为评审或执行准备的事实状态说明，不能作为 `auto` 字段值，也不能单独作为 Case Review 的 `gate_reason`。只有自动化设计本身违反硬门槛时，才可另记为 `design_violation` 且 `gate_reason: true`。

自动化评审只判断设计是否具备自动化适配条件，不执行脚本、不验证正式环境、不验证账号权限或真实数据。实际执行尚未进行时，保留项目执行状态 `not_executed`，并将执行评审标记为范围外；不得把这些事实状态作为 Case Review 的设计门禁失败原因。

## 3. 判定总流程

生成和评审必须对每条用例按同一顺序执行：

```text
1. 确认用例属于自动化判定范围
2. 检查一票否决条件
3. 检查操作是否可机器执行
4. 检查结果是否可形成明确断言
5. 检查数据是否可准备且可清理或隔离
6. 检查关键状态是否可控制
7. 检查用例是否为单一原子测试目的
8. 写入 `auto`，并在评审记录或 HANDOFF 记录满足条件和判定原因
```

硬门槛判定为：

```text
auto=auto
当且仅当：
适用范围满足
AND 不存在一票否决条件
AND 设计上操作可机器执行
AND 设计上结果可形成明确断言
AND 设计上数据可清理或隔离
AND 设计上关键状态可控制
AND 用例只有一个原子测试目的
```

设计上的硬门槛不满足时，判定为 `auto: "no"`。仅当前环境、账号、权限或数据尚未提供时，不视为设计门槛失败，应使用 `auto: "auto"`，并将未就绪项记录为风险、依赖或执行准备项。

定位策略、定位器和页面采集证据不属于判定输入：页面未采集、页面清单未登记、缺少已确认 locator 均不构成门槛失败，也不得据此判定 `no`。

## 4. 自动化必要条件

### 4.1 操作可机器执行

核心动作必须能够映射为机器动作，例如点击、输入、选择、切换、上传、查询、排序、分页、提交、返回和读取结果。需要人工手感、人工判断或无法重复的操作，不满足本条件。

### 4.2 定位策略不作为判定维度

`auto` 判定不检查定位策略、定位器或页面采集证据。操作对象如何在真实页面中定位，由 `07_ui_automation` 依据运行时 DOM、等待策略和执行结果独立处理。

因此：

- 页面未采集、页面清单未登记、缺少已确认 locator，均不得作为判定 `no` 的理由；
- 执行阶段因定位失败导致脚本无法运行，记为 `test_script_error` 或执行阻塞，不得回溯把 `auto` 改为 `no`；
- 定位相关的成败只在评审记录或 HANDOFF 中作为执行准备项说明。

### 4.3 结果具备明确断言

预期结果必须可转换为稳定、可重复的自动化断言，例如元素出现或消失、文本或状态符合要求、数量/日期/金额符合要求、列表发生指定变化、错误提示符合要求、排序/分页/筛选结果符合要求或提交后状态发生变化。

以下表达单独出现时不构成明确断言：

```text
系统运行正常
页面显示正确
用户体验良好
界面美观
操作符合预期
```

### 4.4 数据可清理或隔离

测试数据必须满足以下至少一项：

1. 执行后可删除、恢复、回滚或重置；
2. 数据不能清理，但可以使用唯一编号、独立账号、独立租户、独立项目、独立环境或其他隔离方式，确保用例之间不会互相覆盖；
3. 只读用例使用稳定且不会被其他用例修改的数据。

创建、修改或提交类用例应明确数据准备、唯一标识、清理方式或隔离边界。数据既不能清理，也不能隔离，且结果依赖共享数据状态时，判定为 `auto: "no"`，原因码使用 `uncontrollable_shared_data`。

当前环境尚未提供数据属于执行准备问题，可以使用 `auto: "auto"` 和 `status=blocked`；系统设计上无法控制数据则属于自动化不适合。

### 4.5 关键状态可控制

登录状态、权限、业务状态、日期状态、审批状态、库存/数量状态以及其他影响断言的关键状态，必须可以通过固定前置条件、Fixture、接口、页面操作或隔离环境控制。

状态只是依赖当前线上随机数据、不可控实时数据或不可重复外部状态，且没有稳定夹具或隔离方案时，判定为 `no`。

### 4.6 测试目的原子化

一条用例只能包含一个业务目的、一个状态或条件组合和一套主要数据基线。业务目的允许包含同一业务结果下的关联字段、整体布局、统计字段、公式一致性及必要反向约束；若一条用例同时独立验证不同业务结果、互斥状态/条件、不同数据基线或不同对象，应先拆分用例，再分别进行自动化判定。

共享页面入口、账号、数据准备、操作步骤或定位器，不能作为合并多个独立业务目的的理由。

## 5. 一票否决条件

满足任意一项，直接判定 `auto: "no"`：

- 结果只能依赖人工主观判断，且没有明确可机器判定的标准；
- 依赖实体设备、人工触感、人工观察或无法被系统采集的结果；
- 依赖验证码、短信验证码、人工审批或不可控第三方人工操作；
- 预期结果无法形成稳定断言；
- 关键操作不可重复或不能可靠回放；
- 依赖不可控制的外部系统、实时数据或随机状态，且没有隔离或替代方案；
- 测试数据既不能清理，也不能隔离；
- 用例包含多个无法独立控制和判定的测试目的；
- 需求明确要求人工验收、人工视觉检查或人工合规判断，且没有机器可判定标准；
- 补充 Fixture、测试数据和等待策略后，仍无法可靠执行。

以下情况**不得**作为一票否决理由：页面清单不存在或未登记目标页面、页面未采集或采集状态为 `partial`/`not_captured`、缺少已确认 locator 或截图证据。这些只记录为执行准备项。

一票否决原因必须写入评审记录或 HANDOFF，不得只写“不可自动化”或“条件不足”。

## 6. `auto=no` 与 `auto=auto` 加阻塞的区别

### 6.1 设计上不适合自动化

以下情况使用：

```yaml
auto: "no"
```

并在评审记录或 HANDOFF 记录：`decision=no; status=not_suitable; reason_codes=subjective_manual_judgment,no_observable_assertion; 结果依赖人工主观判断且无法形成稳定断言。`

### 6.2 设计适合但当前条件未就绪

以下情况使用：

```yaml
auto: "auto"
```

并在评审记录或 HANDOFF 记录：`decision=auto; status=blocked; matched=executable_action,observable_assertion,controllable_test_data,controllable_state,atomic_test_purpose; 设计条件满足，但当前测试账号和可回收测试数据尚未准备。`

环境、账号、权限或测试数据尚未确认，通常记录为 `execution_blocker`、风险、依赖或执行准备项，并保持 `gate_reason: false`，不得仅凭这些缺失把设计结论改为 `no`。页面未采集、页面清单未登记或缺少已确认 locator 同样只记录为执行准备项，不得据此判 `no`。但如果这些依赖在系统设计上永远无法控制，则仍应判为 `no`，并可作为自动化设计违规的 `gate_reason: true`。

## 7. 标准原因码

原因码只用于评审记录或 HANDOFF 的说明文字，不写入用例字段。

满足条件原因码：

```text
executable_action
observable_assertion
controllable_test_data
cleanup_supported
isolated_test_data
controllable_state
atomic_test_purpose
read_only_stable_data
```

不适合自动化原因码：

```text
manual_only
subjective_manual_judgment
no_observable_assertion
non_repeatable_action
captcha_or_manual_approval
unstable_external_dependency
uncontrollable_shared_data
uncontrollable_state
multi_purpose_case
```

当前未就绪原因码：

```text
test_data_not_provisioned
permission_not_ready
environment_not_ready
cleanup_owner_pending
external_dependency_pending
```

已移除的定位相关原因码 `stable_locator_strategy`、`unstable_locator`、`locator_evidence_pending` 不得再写入任何产物；历史产物中的旧值仅作兼容读取。

原因码必须与实际证据对应，不得为了满足字段检查而机械填充。

## 8. 生成阶段要求

生成阶段必须：

1. 读取本规则及项目声明的其他适用规则；
2. 先完成每条用例的自动化判定清单，再填写 `auto`；
3. 记录满足条件、未满足条件和判定原因，写入评审记录或 HANDOFF；
4. 保持 `type` 与 `auto` 语义一致；
5. 对 `auto: "auto"` 至少说明操作、断言、数据、状态和原子目的的判定结果；
6. 对 `auto: "no"` 至少说明导致否决的原因；
7. 不把 `auto=auto` 描述为脚本已编写、环境已就绪或测试已通过；
8. 判定结论只写入 `auto`；判定说明不得写入人工字段 `preconditions`、`steps.action` 或 `steps.expected`；
9. 规则缺失、无法读取或与项目 Schema 冲突时停止生成并报告原因。

## 9. 评审阶段要求

评审阶段必须使用生成阶段使用的同一版本规则，逐条重新执行第 3 至第 7 节检查，不得只检查 `auto` 字段是否存在。

评审至少检查：

- `auto` 是否为字符串 `auto` 或 `no`；
- 是否使用了禁止值或布尔值；
- `auto=auto` 是否有必要条件或合理的执行准备说明；
- `auto=no` 是否有具体的一票否决原因；
- 操作、断言、数据、状态和原子目的是否与判定结果一致；
- 生成结论与重新评审结论是否一致。

评审不得因页面清单缺失、页面未采集、缺少已确认 locator 或定位证据未补采，把 `auto=auto` 改为 `no`；也不得要求用例产物包含任何自动化评估结构字段。

评审发现生成的 `auto` 与规则不一致时：

- 设计条件不满足但标记为 `auto`：记录自动化判定设计违规，并要求返工；
- 设计条件满足但标记为 `no`：记录为自动化候选遗漏或待确认项，不得无证据强制改写；
- 仅因环境、账号、权限或数据暂未就绪：记录 `blocked`/依赖，不得当作设计不适合自动化；
- 字段非法、原因缺失或状态和值矛盾：记录结构或设计违规；
- 评审不得未经用户明确授权直接改写 `04_testcases`。

## 10. 边界案例

| 场景 | 判定 |
|---|---|
| 只读列表查询，数据稳定且结果可断言 | `auto=auto`，可使用 `read_only_stable_data` |
| 新建订单，使用唯一编号，执行后可删除 | `auto=auto`，使用 `cleanup_supported` |
| 审计日志不能删除，但每次使用唯一业务编号并按该编号断言 | `auto=auto`，使用 `isolated_test_data`，记录数据增长风险 |
| 有清晰页面步骤，但结果只有“体验良好” | `auto=no`，使用 `no_observable_assertion` |
| 需要短信验证码或人工审批 | `auto=no`，使用 `captcha_or_manual_approval` |
| 设计条件完整，但测试账号暂未申请 | `auto=auto`，在评审记录或 HANDOFF 记录 `permission_not_ready` |
| 页面未采集、页面清单未登记或尚未有真实 locator，但步骤可机器执行、断言明确、数据与状态可控 | `auto=auto`，定位问题记为执行准备项 |
| 只能依赖共享线上随机数据，无法清理或隔离 | `auto=no`，使用 `uncontrollable_shared_data` |
| 同一业务结果下验证关联字段、整体布局或公式一致性 | 可合并；按一个业务目的评估自动化，不因断言数量机械降级 |
| 一条用例同时验证多个互斥状态/条件或多套数据基线 | 先拆分；未拆分时 `auto=no`，使用 `multi_purpose_case` |

## 11. 阶段边界

本规则不替代：

- 测试设计规则中的覆盖、原子性和状态分支要求；
- YAML/Markdown Schema 校验；
- UI 自动化脚本编写；
- 真实 UI 执行和执行 readiness；
- 禅道同步及真实回读。

`auto` 只用于标识自动化设计候选。UI 自动化阶段仍需根据真实 DOM、等待、Fixture、执行环境和运行结果独立判断是否可以执行；该阶段的定位成败与执行结果不影响本规则的 `auto` 结论，也不得反向改写用例的 `auto`。
