# 测试设计增强规则

## 适用范围

本规则适用于依据需求、分析资料和测试计划生成或评审的独立 UI 测试用例。`page.json`、`design.json` 如存在，仅作为普通参考资料，不参与页面证据检查或阶段门禁。规则只约束后续生成和评审行为，不追溯修改历史用例、评审结果、自动化产物或执行结果。

本规则是测试设计要求的唯一来源。生成器和评审器不得通过关键词存在、字段存在或摘要内容代替逐条执行本规则。

## 规则加载与适用性

1. 执行生成或评审前，必须识别当前项目声明的适用规则，并读取本规则的完整内容。
2. 规则缺失、无法读取、版本不明确或与其他适用规则发生冲突时，必须停止当前生成或评审，并报告具体原因。
3. 规则适用范围由当前任务、项目配置、需求资料和输入产物共同确定；不得把其他项目的业务专项规则当作本通用规则的固定要求。
4. 生成和评审必须引用同一份已读取的规则内容，并记录规则名称、版本或其他可追溯标识及检查结论。

## 页面入口与前置条件

1. 每条独立 UI 测试用例的 `preconditions` 只描述执行前必须具备的静态条件，包括账号、权限、环境、浏览器、数据和初始业务状态。
2. `preconditions` 不得写入进入系统、点击菜单、进入模块、打开目标页面、切换目标 Tab、打开弹窗/抽屉等导航动作，也不得用“已打开页面”“已进入列表”替代导航步骤。
3. 不强制在人工用例中写具体登录步骤、正式环境 URL 或测试租户；如项目或测试计划另有统一入口约定，按其约定表达，但不得因此把页面已打开作为前置条件。
4. 前置条件必须按实际必要数量生成；删除某项后若不影响当前原子目的和唯一判定，不得保留该项。定位器确认、自然唯一业务键、行级作用域和其他行防误判属于自动化实现条件，除非需求明确将其作为业务验收条件，否则不得写入人工前置条件。
5. 页面入口应使用项目配置、需求资料、分析资料或普通页面参考资料中已确认的信息，不得凭空补充菜单层级、路由或页面名称。

## 测试步骤起点

1. 适用时，`steps.action` 必须从登录/授权入口开始，依次写明进入门户、点击菜单、进入模块和打开目标页面等可执行导航动作；如项目明确提供已认证会话，应写明该已确认入口动作。
2. 导航步骤的 `steps.expected` 必须写出足以判定业务到达的可观察结果，例如页面标题、目标区域、筛选区、状态统计区、列表容器或加载/权限提示状态。
3. 页面到达结果属于对应导航步骤的预期，不得只写在 `preconditions`，也不得用“已进入页面”替代导航动作。
4. 页面到达确认后，后续步骤从目标页面内的被测操作开始；不得为了补充导航而加入当前测试点未验证的功能、页面或分支。
5. 步骤和预期按最小充分原则生成：每个步骤只保留完成核心判定所需的主要动作，每个预期只确认该动作对应的可观察业务结果；删除测试显示不贡献于当前原子目的的动作、重复到达确认、技术定位动作和范围声明。

## 操作对象与预期

1. 每个 UI 步骤必须明确页面区域、控件或字段以及操作；不能只写无法识别对象的泛化动作。
2. 输入、选择、点击、切换、排序、分页等操作必须写明实际对象，并优先使用需求、分析资料或普通页面参考资料中的可见名称、字段标识、`name` 或 `placeholder`。
3. `action` 中的操作对象及其自动化字段（如存在）必须彼此一致；自动化脚本的定位方式由真实 DOM、脚本和执行结果独立验证。
4. `expected` 必须描述与当前操作对应的可观察、可判定结果，不得只写“成功”“正常”或其他无法验证的结论。
5. 不得通过字段名、定位器或数据值让执行者自行推断未写明的操作对象、范围或判定标准。

## 步骤操作粒度与导航拆分

1. 一个 `steps` 项应描述一个主要操作，或为完成同一目标而必须连续、紧密执行且不可合理中断的动作单元；每个步骤都必须有覆盖该动作单元的可观察、可判定预期。
2. 相邻动作只有在同时满足以下条件时才允许合并：服务于同一测试目标；需要连续执行；前一动作的结果仅作为后一动作的执行条件；动作之间不存在可单独观察、单独失败或单独判定的中间结果。合并不是默认行为，不能仅因动作发生在同一页面、共享对象或经常连续执行而合并。
3. 访问入口并完成对象选择、展开层级并进入目标页面、定位目标对象并执行其后续入口操作等抽象的连续动作，可以在满足第2项条件时合并为一个步骤；`action` 必须写完整动作链，不能省略中间动作，`expected` 必须确认动作链的最终可观察结果。
4. 存在独立执行结果、独立失败原因、独立观察对象或独立判定标准的动作必须拆分为独立步骤。页面到达、对象定位、业务操作、结果展示和结果校验是否独立，应依据当前用例的测试目的和覆盖目标判断，不得一律合并或一律拆分。
5. 不得通过连接词掩盖多个互不满足合并条件的操作，也不得为追求形式上的原子性而把同一连续动作链拆成缺乏独立判定价值的过细步骤。拆分后，前一步预期只能确认前一步动作的结果；合并后，最终预期不得遗漏动作链中仍需保留的操作对象和到达证据。
6. 生成或评审后逐条检查相邻 `steps` 是否满足合并条件，以及单个 `steps.action` 是否包含不满足合并条件的多个动作；不满足合并条件时拆分并补充对应预期，满足合并条件且拆分不会增加独立判定时允许合并。

## Casely 风格优先级与测试点原子性

1. 标题必须表达业务条件或动作、操作对象和可观察业务结果；步骤必须按业务发生顺序且可由测试人员直接执行；预期必须可观察、可判定并说明比较对象或业务依据。历史用例结构、字段式标题或“功能正常”等不可判定表达与本要求冲突时，以本要求为准。
2. 每条用例只能对应一个业务目的、一个核心测试结果和一套独立数据基线；业务目的不是单个字段或单个断言，而是同一业务结果下可整体裁决的验证单元。
2. 同一业务目的、同一套数据基线下，关联字段、整体布局、统计字段、公式结果及必要反向约束可以放在同一用例；不同数据基线、互斥状态/条件、不同业务对象或不同业务结果可以分别通过或失败时，必须拆分为不同用例。
3. 已打开的同一个控件、弹层或下拉内，列举其组成选项或按钮是否齐全，属于该控件的一次完整性判定，不是复合 `expected`。判定对象是“该控件已完整展示”，不是每个组成项各自的业务生效。例如：日期弹层显示昨天、今天、明天、自定义日期、重置和确定，可写在同一条 `expected`。
4. 下列情况仍须拆分：不同页面区域（如日期筛选区与发货单列表）；不同业务结果（如弹层仍打开且列表尚未按新日期刷新）；互斥分支（如确认昨天、确认今天、确认明天、确认自定义须各一条）；正负混合或“或”结果（如空状态或引导）。
5. 不得使用“依次验证”或复合 `expected` 掩盖多个独立判定，也不得因为共享页面入口、前置条件、数据或定位器而合并测试点。
6. 用例重复评审只比较不同用例的主测试点，包括核心业务行为、状态或条件分支、被测结果和独立判定标准；登录、菜单导航、进入页面、页面标题/菜单高亮/加载状态验证等页面到达证据属于过程性步骤，不计为主测试点。不同用例仅因共享过程性步骤不得判定为重复。
7. 行为验证、结果展示、统计口径、数据计算、筛选、排序、分页、权限和异常处理等内容，只有在对应不同业务结果、不同数据基线或可独立定级时才分别建模；同一业务结果下的关联字段、整体布局、统计范围、公式一致性和必要反向约束可合并。是否拆分以业务目的、数据基线和独立判定标准为准。
8. 生成和评审必须使用同一套 `merge`/`split` 判定：仅当检查项位于同一页面、使用同一数据基线、操作同一业务对象、沿同一连续动作链并验证同一业务结果，且每项可独立定位失败时，才允许合并；页面切换、不同数据基线、不同对象、互斥状态/条件、不同业务结果、独立重置或失败不可定位时必须拆分。合并必须保留主用例、来源用例、覆盖目标、原子目的和步骤/预期映射；跨页面不得仅因共享业务数据或最终结果合并。
8. 标题、`steps`、`expected`、`test_data` 和追溯信息必须围绕同一个业务目的保持一致。发现多个核心业务目的时，必须先拆分业务目的，再生成用例。

## 分类、状态与统计覆盖

1. 对需求定义了多个分类、状态、分支或统计维度的测试，必须覆盖当前范围内全部适用项。
2. 每个分类、状态或统计维度必须具有独立的操作依据、数据口径和可判定预期；不得用单个项的结果推断其他项。
3. 行为切换、结果列表变化与统计口径校验属于不同测试目的时，必须拆分为不同用例。
4. 统计校对应保持相同且已确认的筛选、数据和环境基线，并明确当前分类或状态对结果的影响。
5. 某项的规则、数据或证据不足时，必须保留待确认或阻塞说明，不得猜测统计数字、计算规则或覆盖结论。

## 优先级划分

1. 测试用例优先级采用 `P1`-`P4` 四级，`P1` 最高、`P4` 最低；每条用例必须且只能填写一个优先级。
2. 优先级按业务影响、失败后果、使用频率和可替代性综合判定；不得按测试类型、模块名称或用例数量直接映射优先级。
3. 四级定义与判定标准：
   - `P1` 阻断级：核心业务流程无法继续、功能整体不可用、关键数据严重错误或数据丢失。
   - `P2` 高优先级：核心功能可操作，但业务结果、数据口径或统计结果错误，影响较大且缺少替代方案。
   - `P3` 一般优先级：非核心或低频、边界场景异常，存在替代操作，不阻断主要流程。
   - `P4` 低优先级：不影响业务功能、数据正确性和核心流程，主要为文案、样式、提示和交互体验问题。
4. 定级必须按固定业务影响判定链执行：先判断核心流程是否无法继续或关键数据是否严重错误；再判断业务结果/统计口径是否错误及影响范围；再判断是否属于低频、边界或非核心场景且存在替代操作；最后判断是否仅影响文案、样式、提示或操作体验。每条复核记录必须显式说明核心流程阻断、关键数据影响、业务影响区域、使用频率和替代路径。
5. 优先级是原子测试目的的属性，一个原子测试目的只能对应一个优先级；同一用例覆盖多个可独立定级的影响时，必须先按原子目的拆分用例，再分别定级。
6. 边界、异常和兼容类问题不因测试类型自动降级；其失败会导致关键业务数据或结果错误时，应按实际影响定级。功能类问题若只影响低风险展示或体验，应按实际影响下调。不得按模块、测试类型、来源优先级、用例数量或“正常/异常”标签机械继承。
7. 每条理由必须说明失败后的具体业务后果、是否存在替代路径以及定级依据，并能追溯到需求、分析资料或测试计划。以下理由无效：仅写“沿用来源优先级”“模块重要”“属于核心页面”“与需求一致”或仅重复测试类型。
8. 优先级分布仅作为控制性观察参考：`P1` 约 `5%-10%`，`P2` 约 `25%-35%`，`P3` 约 `45%-55%`，`P4` 约 `10%-20%`。偏离时必须记录实际比例、具体偏离原因和可追溯的特殊业务依据；分布偏离本身只能生成提示/观察项，不得设置门禁失败，也不得为满足比例擅自改写优先级。
9. 影响后果无法判定，或缺少需求、数据、证据支撑时，按不完整证据处理要求保留待确认，不得猜测定级；依据不足属于证据风险或相应输入问题，不得用分布比例替代业务判断。

## 页面资料边界

1. 页面清单与页面采集结果不是测试设计或评审的维度，也不作为任何字段的判断条件；`page.json`、`design.json` 是否存在、是否登记目标页面、采集状态为 `partial` 或 `not_captured`，均只可记录为 `evidence_risk` 且 `gate_reason: false`，不得设置 `gate_reasons`、`blocked`、`input_missing`、`missing_design` 或拒绝交接。
2. 定位器来源、页面/元素映射和页面引用一致性不参与检查；定位成败由 `07_ui_automation` 依据真实 DOM 独立处理，不得把页面清单存在性作为门禁。
3. 正式 URL、菜单承接、运行环境、账号权限、脱敏数据、可回收提交数据和清理责任只能记录为风险、依赖、执行准备项或未确认项；正式 UI/自动化执行阶段的 readiness 规则不受本条影响。

## 不完整证据处理

1. 入口、数据、权限、环境或实际执行资料处于项目约定的阻塞、部分采集、缺失或待确认状态时，必须在现有阻塞、追溯字段或评审记录、HANDOFF 中如实记录。
2. 证据不足可以生成带阻塞或待确认状态的用例，但不得把猜测内容写成已确认，不得把不可执行写成可执行，也不得把未执行写成通过。
3. 证据阻塞不豁免测试设计规则；即使证据不完整，用例仍必须满足原子性、步骤起点、操作对象和预期表达要求。
4. 补充页面入口或字段描述不等于完成真实 UI 执行，不得因此改变自动化状态、执行结果或评审结论。

## Casely 风格合并审计

生成阶段必须在输出前记录连续检测项分组和合并审计；评审阶段必须复核该审计并对未登记的相似候选执行同样判定。审计至少包括 `merge_decision`、`primary_case_id`、`source_case_ids`、共享页面/数据/动作/结果、保留的 `coverage_ids`、`atomic_purpose_ids`、步骤/预期映射和 `failure_localization_supported`。应使用现有 `trace`、评审说明或 handoff 承载，不新增 Schema 字段。

## 生成流程与自检

生成每条用例前，必须按以下顺序执行：

1. 读取适用规则及其版本或标识。
2. 读取需求、分析资料、测试计划和项目提供的入口信息；页面资料如存在，仅作普通参考。
3. 先建立原子测试目的清单，标明每个目的的范围、数据基线、判定标准、优先级和证据状态；同时建立覆盖目标、页面板块和计划范围的集合索引。
4. 根据原子测试目的生成用例，不得直接复制历史用例结构作为新用例设计依据；每条用例必须回填合法的 `coverage_ids`、`plan_item_ids` 和 `atomic_purpose_ids`。
5. 生成前后执行三类集合检查：分析覆盖目标 → 测试用例、测试计划范围项 → 原子测试目的/测试用例、测试用例 → 合法覆盖目标；检查应使用集合索引，不能以摘要或关键词命中替代。
6. 证据不足时保留至少一个 `blocked` 设计用例；覆盖目标无用例时必须输出 `missing_design`，并阻断阶段交接。
5. 生成后逐条对照本规则检查，并记录通过项、设计违规项、证据阻塞项和未确认项。

自检必须覆盖本规则中适用于当前用例的全部章节，至少确认：

- `preconditions` 只包含静态执行条件，不包含菜单或页面导航动作；
- 步骤包含适用的页面入口动作，导航步骤预期包含页面到达证据，后续步骤从页面内被测操作开始；
- 操作对象、定位器、证据和预期彼此一致；
- 用例只有一个原子测试目的和独立判定标准；
- 不同用例的主测试点已完成重复检查，公共页面到达证据未被计入重复；
- 所有适用分类、状态、分支和统计维度均被独立覆盖；
- 每条用例只有一个优先级，且按统一判定顺序定级，未因测试类型直接映射，分布未异常膨胀；
- 不完整证据已如实标记，未将猜测或未执行内容写成通过；
- 当前模块的适用操作均已关联成功正向用例，或明确记录 `not_applicable`/`unconfirmed` 及理由；
- 成功用例包含触发结果和业务回读证据，未将按钮可见、表单打开或确认弹窗当作成功覆盖。

## 覆盖账本门禁

1. 分析产物中的每个 `coverage_id` 必须在用例集合中有归属，或明确为 `out_of_scope_with_owner` 并填写责任 `req_id`。
2. 计划范围项必须至少关联一个原子测试目的和一个用例；用例必须只引用当前需求合法覆盖目标。
3. `blocked` 仅表示环境、权限或数据不足，不表示缺少设计；`missing_design`、孤立用例或无效 `coverage_id` 属于设计或追溯错误，必须阻断交接。`capture_id`、`page_id`、`state_id` 等页面资料字段不属于本规则门禁。
4. `L1` 页面/板块出现、`L2` 字段展示、`L3` 字段值/计算/跨系统/视觉正确性必须分别检查，不得以低层级覆盖高层级。

## 条件适用的操作与核心流程覆盖

1. 不得把创建、查询、更新、删除、状态切换、导入、导出、刷新或重置中的任何操作设为所有模块的固定必选项；只有需求、分析资料、测试计划或已确认的业务页面资料明确表明该模块存在对应按钮或业务能力时，该操作才属于 `applicable`。
2. 生成前必须建立模块级操作能力清单，至少记录 `operation_capability`、来源依据、`applicability`、业务理由、成功结果、数据/状态变化、回读证据和清理责任。`applicability` 只能是 `applicable`、`not_applicable` 或 `unconfirmed`。
3. `not_applicable` 必须有可追溯的业务理由；不得因按钮名称未命中、页面资料缺失或当前环境不能执行而直接判定不适用。资料不足时使用 `unconfirmed` 或记录 `evidence_risk`。
4. `applicable` 操作必须至少关联一个成功正向用例。成功覆盖必须包含触发/提交动作、成功反馈，以及列表、详情、状态、文件或其他业务结果的回读证据；仅验证按钮可见、表单打开、字段回显、确认弹窗、取消或失败校验不算成功覆盖。
5. `applicable` 且没有成功正向用例属于 `missing_design`/`design_violation`，必须阻断交接；`unconfirmed` 只能保留待确认项，不得伪造已覆盖或不适用结论。
6. 已生成成功用例但环境、权限、数据或清理条件不足时，记录 `execution_blocker`，不得删除、降级或改写为 `not_applicable`；该阻塞本身不构成设计门禁。
7. 对同一能力存在多个互斥状态或结果时，仍按原子目的和状态分支规则分别建模；适用性清单只决定是否需要覆盖，不替代成功结果和分支覆盖检查。

## 失败处理与评审门禁

1. 规则读取失败、规则冲突或无法判断规则适用范围时，当前阶段不得完成。
2. 测试设计违规属于阻断问题：必须返工、重新自检并重新评审，未修复前不得生成完成交接或下游通过结论。
3. 环境、权限或数据不足属于独立的执行阻塞问题：可以保留用例，但必须明确记录 `execution_blocker` 且 `gate_reason: false`；页面清单或页面参考资料缺失属于 `evidence_risk` 且 `gate_reason: false`。UI、Playwright、有头浏览器、自动化实际执行、PICT 实际执行、CSV 生成和远程同步默认属于执行阶段，不纳入本轮设计评审门禁；应记录为范围外或后续执行准备项。
4. 一般格式、表达或可维护性问题应单独记录，不得掩盖设计违规或证据阻塞。
5. 评审必须复核生成阶段使用的同一规则，按规则逐条检查实际用例结构和语义，不得只检查字段、关键词或文档摘要。
6. 评审交接必须包含规则标识、检查范围、设计违规、证据阻塞、未确认项和最终门禁结论；不得因历史产物存在而自动放宽本规则。

## 跨用例职责唯一性

1. 生成前必须建立全量职责矩阵，至少记录每条用例的业务对象、初始状态、触发动作、分支条件、核心业务结果、数据影响、验证层级、`atomic_purpose_ids` 和追溯关系；不得只按需求覆盖项逐条生成。
2. 每条用例必须生成可审计的行为指纹：`业务对象 + 初始状态 + 触发动作 + 分支条件 + 核心结果 + 数据影响 + 验证层级`。标题、原子目的不同不等于职责不同，比较必须以步骤和预期中的主测试点为准。
3. 生成前后必须对全量用例执行相似职责检查，重点检查状态/条件、权限、提交状态、页面状态、数据一致性、筛选、输入校验、空态、公式、异常和跨页面联动等场景；不得只检查重点需求组。
4. 相似候选必须先拆分复合职责，再逐项判断：`retain`、`retain_and_narrow`、`merge`、`split` 或 `delete`。仅共享登录、导航、页面到达、公共前置条件或定位策略，不构成职责重叠。
5. 两条用例只有在核心行为、状态/条件分支、被测结果和独立判定标准均相同，且不存在不同验证层级或独有风险时，才可合并或删除；不同验证层级可以保留，但必须删除跨层级重复断言，并在评审中说明边界。
6. 每条保留用例必须回答“删除本用例后哪个独有风险不再覆盖”。无法回答时，必须收窄、合并或删除；同一行为的不同输入值应优先通过分支/参数矩阵表达，不得仅替换输入值复制用例。
7. 生成交接前必须输出职责唯一性检查结果：全量检查数量、相似候选、重叠点、独有职责、处理决定和未确认项。未解释的重复候选属于 `design_violation`，不得仅以覆盖完整或优先级合理通过。

## 兼容性与边界

1. 本规则不新增测试用例字段，不改变现有 YAML、Markdown、需求追溯或自动化评估结构。
2. 测试用例 YAML 文件必须符合 `.agents/references/testcase-yaml.template.yaml` 的实际格式要求；测试用例 Markdown 文件必须符合 `.agents/references/testcase-markdown.template.md` 的实际格式要求。检查范围包括模板规定的结构、层级、字段、字段类型、必填项、枚举值、步骤表示和内容组织方式。
3. 生成、修改和交接前，必须分别依据上述 YAML 和 Markdown 模板检查对应文件；若项目存在适用的 Schema 或校验脚本，还必须执行项目约定的校验。模板或校验不通过属于结构或交接阻断，不得通过文字说明、字段补注或忽略未检项替代，也不得以其他格式的 Schema 校验结果替代模板要求。
4. 本规则不替代项目专项业务规则、Schema、脚本校验器、真实 UI 执行或远程系统同步流程；模板要求与其他适用约束均须同时满足。
5. 本规则文本本身不是机器校验器；生成和评审 Agent 必须依据本规则执行结构化检查并如实记录结果。
6. 评审阶段必须把同目录测试用例 YAML 与 Markdown 作为一对交付物进行逐条对齐校验：YAML 是 `auto` 和明细事实源，必须核对数量、ID、标题、优先级、`auto`、类型、原子目的、追溯、步骤 action/expected 及汇总统计；缺失或不一致属于结构/交接阻断，记录差异和门禁原因，不得给出无条件通过。
7. 历史用例和历史评审产物只能作为检查对象或参考，不得因本规则自动改写。

## 范围边界与人工可执行性

1. 生成前必须为每个计划范围项标明 `in_scope`、`out_of_scope` 或 `out_of_scope_with_owner`；只有 `in_scope` 目标可生成当前需求的人工操作和断言。
2. `out_of_scope_with_owner` 只能保留在计划、覆盖账本、依赖或追溯字段中，并必须填写责任需求；不得以范围说明步骤补偿覆盖账本。
3. 人工用例的前置条件只描述执行前必须具备的账号、权限、环境、浏览器、数据和初始业务状态；不得写入进入菜单、进入页面、打开弹窗/抽屉、切换 Tab 等导航动作，也不得写入“已打开页面”来替代步骤。不得写入“已应用非状态筛选基线”“不执行某操作”“真实数据未提供”等内部规划语句。证据阻塞应记录在 `trace.status`、`zentao_status`、评审记录或 HANDOFF。
4. 操作必须是测试人员可以直接执行的点击、输入、选择、查看或对照动作；期望必须是页面可观察的字段、提示、状态、数量、排序或数据变化。
5. 禁止人工文本直接出现源文件名、页面证据文件、内部状态 ID、数据库/API 字段名、实现布尔属性、CSS/定位器、自动化框架术语或英文内部状态。内部证据统一放入现有机器追踪字段；业务字段使用页面中文名称，例如“实际可发数为 0”。
6. 用例生成后必须执行文本隔离检查：`preconditions`、`steps.action`、`steps.expected` 中不得出现范围声明式短语（如“本用例不测”“不进入明细”“不执行导出”）或技术证据词（如 `page.json`、`sortable=false`、`actual_available`、`state_id`、`st-default`）。命中即阻断交接。
7. 删除多余步骤后必须复核覆盖账本；范围边界应由 `coverage_ids`、`plan_item_ids`、`atomic_purpose_ids` 和责任需求映射表达，不能由人工用例数量或否定性步骤表达。

## 原子目的与状态分支拆分门禁

1. 生成前必须把每个测试目标拆成原子目的清单，每个原子目的至少明确：核心行为、唯一状态或条件组合、数据基线、可观察结果和独立判定标准。
2. 当同一页面行为受多个状态、日期、权限、分类或条件组合影响时，必须先建立状态/条件分支矩阵，再决定用例数量；矩阵中的每个可独立通过或失败的分支都必须对应独立用例。
3. 共享页面入口、账号权限、数据准备、操作步骤或定位器，不得作为合并多个原子目的的理由。
4. 一个用例只能引用一个原子目的和一套核心判定。`atomic_purpose_ids` 出现多个值，或同一 `expected` 同时验证多个互斥状态、多个条件分支、多个负向结果时，必须拆分；若现有字段结构不支持表达，应在评审中记录设计违规，不得猜测新增字段。
5. 同一套数据基线、同一动作或连续动作链、同一业务结果下，多个可观察表现可以保留在同一个用例中，但必须拆成多个连续步骤：触发动作后先验证动作结果，再通过独立步骤回读或核对关联字段/公式。该规则是步骤粒度要求，不构成新增用例；不同数据基线、互斥状态/条件、不同对象或不同业务结果仍须拆分用例。
6. “以及、同时、分别、依次、均、都应”、顿号或“和”只是核对信号，不得仅凭并列连词判定复合。并发场景中“分别”仅描述同一数据基线下的两个执行端时，不得据此判定多个业务分支；必须结合数据基线、动作链和结果判定确认。必须先判断这些项是否同属一个已打开控件的组成元素：是则视为该控件一次完整性判定，允许写在同一 `expected`，无需记录合并理由；不是才按复合用例拆分。正例：日期弹层显示昨天、今天、明天、自定义日期、重置和确定。反例：日期筛选区与发货单列表同时可见；弹层仍打开且列表未刷新；确认昨天与确认今天写在同一条；空状态或引导二选一。
6. 标题、前置数据、步骤、预期和追溯必须指向同一状态或条件分支。标题只写“满足条件”但预期又包含多个排除状态时，属于标题与判定不一致的设计违规。
7. 正向场景和任一负向场景、不同互斥状态、不同边界分支不得共用一条用例；每个可独立通过或失败的状态、条件或结果均应分别建模。同一控件内的组成项展示不是互斥分支。
8. 证据不足时可以为每个已识别分支保留 `blocked` 用例，但不得把多个分支合并后以一个 `blocked` 掩盖原子设计缺失。
9. 对同一字段或状态存在多个互斥业务区间时，必须先建立“条件区间/状态 → 独立用例”的分支矩阵；每个区间都要有独立标题、前置数据、步骤和唯一预期。不得使用“分别查看”“覆盖以下情况”“依次验证”或一个决策表预期替代分支用例。
10. 对状态由多个条件共同决定的场景，边界值、开区间、闭区间、前置状态和后置状态均视为独立条件组合。共享页面入口、权限、数据前缀或操作步骤不能作为合并理由；只有测试目的、条件组合和独立判定完全相同才允许合并。
11. 单用例必须遵循“一条用例、一个业务结果、一套数据基线”：同一验证点若需要多套互斥业务数据才能满足全部预期，必须拆分为独立用例；同一套数据基线的同一动作链可以通过多个连续步骤验证动作结果、回读结果和关联一致性，不得仅因“分别/依次”描述并发执行端而拆分或误报。
12. 对发货进度/状态组合，至少分别建立：0%→待发货、(0%,100%)→发货中、100%且待出雏→发货中、100%且已出雏且未签收→已发货、100%且全部签收→已签收五个独立分支。合并任意两个分支均记录 `design_violation`，不得降级为 `blocked`。
