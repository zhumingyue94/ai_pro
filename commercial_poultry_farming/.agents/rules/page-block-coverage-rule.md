# 业务板块覆盖规则（测试用例）

## 原子状态分支拆分补充

同一页面字段或状态存在多个互斥业务条件时，必须按条件组合建立独立用例，不得在一条用例中用“分别查看”“依次核对”或决策表预期合并。每个分支需独立描述前置数据、操作对象和唯一可观察结果；共享页面入口和测试数据准备不构成合并依据。

## 适用范围

- `stage-requirements-analysis-agent`：输出或引用页面板块、信息项和数据源矩阵。
- `stage-test-plan-agent`：将页面板块纳入范围、策略和风险规划。
- `stage-testcase-generation-agent`：生成板块级可执行步骤和断言。
- `stage-case-review-agent`：检查板块和字段覆盖完整性。

不生成或评审测试点，不依赖 `TP_*`、`tp_id` 或测试点评审文件。

## 覆盖层次

| 层次 | 问题 | 用例要求 |
|---|---|---|
| L1 | 页面、弹窗、抽屉或 Tab 是否出现 | `steps.action` 指明进入菜单/页面/弹窗/抽屉/Tab 的入口动作；对应 `steps.expected` 写出标题、菜单高亮、板块或区域名称等到达证据 |
| L2 | 板块展示哪些字段、列、指标、标签 | 步骤/预期点名具体信息项 |
| L3 | 信息是否正确 | 预期写出可观察值、计算关系或跨模块一致性判定 |

## 要求

1. 每个需求范围内的业务板块、弹窗、抽屉和 Tab 都应有覆盖记录；没有页面清单条目不得阻塞生成或评审。
2. 复杂页面先由分析或测试计划形成 `page_block_specs` / `ui_matrix`，再生成用例。
3. 关键板块必须覆盖字段和正确性，不得用一条“展示正确”替代整页覆盖。
4. 步骤必须写清板块、控件和操作对象；页面、弹窗、抽屉或 Tab 的进入动作必须写入 `steps.action`，对应到达证据必须写入 `steps.expected`，且预期必须可观察、可裁决。
5. 多板块且产生不同业务结果时拆分步骤或预期；同一板块的整体布局、关联字段、统计字段和公式一致性可在同一业务目的下共用一套断言。
6. 同一板块的同一业务目的若需要多套互斥业务数据，必须为每套数据建立独立原子测试目的和独立用例；不能以“覆盖全部状态”或决策表预期替代分支用例。
6. 需求、原型或分析没有提供板块事实时，记录待确认，不得按常见后台页面臆造。

## 覆盖账本追溯

复杂业务板块的 `page_block_specs` 如存在可关联 `coverage_id`。每个覆盖目标分别记录 L1/L2/L3 设计层级，并沿“目标 → 计划范围项 → 原子测试目的 → 用例”追溯。评审执行集合检查：

- 分析覆盖目标到用例：无归属用例为 `missing_design`；
- 测试计划范围项到原子目的/用例：无覆盖为 `missing_design`；
- 用例到合法覆盖目标：孤立用例或无效 `coverage_id` 为错误；
- `blocked` 必须保留设计用例，`out_of_scope_with_owner` 必须有责任需求；
- 需求、计划、原子目的和用例之间的业务追溯必须一致；`capture_id`、`page_id`、`state_id` 等页面资料字段不属于本规则门禁。

L1 页面/板块出现、L2 字段展示、L3 字段值/计算/跨系统/视觉正确性不得相互替代。

## 评审门禁

`stage-case-review-agent` 对缺失业务板块、字段、正确性判定、`missing_design` 或孤立业务覆盖记录为 `design_violation` 或 `traceability_failure`，并标记 `gate_reason: true`；页面清单、页面映射、元素映射和页面引用不一致属于 `evidence_risk`，标记 `gate_reason: false`。`page_inventory_partial`、`formal_route_not_explored` 和 `authorized_data_missing` 也不得作为用例评审的 `gate_reasons`、blocking gate 或 `gate_passed: false` 的失败依据，只能记录为风险、依赖、执行准备项或未确认项。UI、Playwright、有头浏览器和正式页面执行属于后续执行阶段，不纳入本轮设计评审；执行尚未进行时不得据此否定设计门禁。门禁使用 `report_only`，但必须按所有 `gate_reason: true` 项计算，不得伪造通过。

## 范围边界与人工文本隔离

1. 测试计划中的 `out_scope`、`owner_req_id` 和依赖只用于范围账本、风险、依赖及交接说明；不得复制为人工用例步骤、前置条件或期望结果。
2. 当前需求只生成本需求负责的可观察验证。由其他需求承接的导出确认/文件下载、明细追溯或业务执行，不得在本需求用例中通过“本用例不测”“不进入”“不执行”等否定性步骤声明。
3. 页面可见性属于当前需求范围时，只描述页面上可见的按钮、列或区域；具体交互属于其他需求时，保留责任需求映射，不扩展人工操作。
4. `preconditions`、`steps.action` 和 `steps.expected` 是人工执行文本，只能使用页面可见名称、业务字段和可观察结果；其中 `preconditions` 只描述静态执行条件，不承载页面导航动作；`ui_source`、`state_id`、`locator_ref` 等机器证据字段不得泄漏到人工文本。
5. 发现范围越界、范围声明式步骤或技术字段泄漏时，评审必须记录为设计违规，而不是一般表达警告。

## 原子场景与互斥状态覆盖

1. 页面板块覆盖说明页面对象和信息层级；同一板块的列名、状态卡、控件组成项和关联统计字段属于整体展示或同一业务结果时，可以在一条用例中完整验证，不得机械按字段拆分；多个状态分支的可见性或可用性判定仍不得压缩到一条用例中。
2. 同一板块中，若某入口、按钮、标签或数据行在不同状态/条件下有不同结果，必须为每个可独立判定的分支建立独立覆盖目标或原子测试目的，并分别追溯到用例。
3. 正向可见、负向不可见、状态 A 不可用、状态 B 不可用等互斥结果不得共用同一套断言；共享页面入口不改变拆分要求。
4. 评审必须检查“覆盖目标 → 分支/原子目的 → 用例”的一对一归属。一个用例承载多个互斥分支，或某个分支没有独立用例，均记录为 `design_violation`；证据阻塞不能替代分支设计。
5. 对状态分支较多的页面，分析或测试计划应保留分支矩阵及合并理由；没有矩阵或合并理由时，不得以“展示正确”“按条件显示”等摘要结论认定覆盖完整。
