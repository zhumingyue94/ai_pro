# Casely 测试用例风格指南

> 本文件是仓库内各项目测试用例生成与评审的公共风格参考，依据已确认的测试用例及评审记录整理。
> 文中的“种禽孵化管理系统”及菜单、字段、业务对象只属于示例；实际项目术语、权限、数据和业务规则以项目资料为准。
> 现有测试用例的数据结构和交付契约仍以根目录 `.agents/references/testcase-markdown.template.md`、`.agents/references/testcase-yaml.template.yaml` 及项目校验规则为准。

## 1. 适用范围

后续生成或人工编写用例时，重点统一以下字段：

- `标题`
- `前置条件`
- `步骤`
- `预期`

不得在本文件中新增账号、密码、定位器、CSS、POM、Fixture 或其他敏感/自动化实现细节。

## 2. 总体写法

- 使用简体中文，保留项目已有业务术语和中文全角标点。
- 使用 Markdown 字段标记：`**标题**`、`**前置条件**`、`**步骤**`。
- 每条用例只验证一个业务目的和一套数据基线；业务目的不是单个字段或单个断言。
- 同一业务结果下，同一套关联数据的多个字段、整体布局、统计字段、公式结果和必要反向约束可以写在同一条用例中；不同数据基线、互斥状态/条件、不同业务对象或不同业务结果必须拆分。
- 步骤按用户实际操作顺序编号。
- 每个操作步骤后立即写一条同级缩进的 `- 预期：`。
- 预期必须描述可观察、可核验的结果，避免只写“操作成功”“显示正常”等不可验证表述。
- 标题、前置条件、步骤和预期中的对象名称保持一致，不随意改写页面或业务术语。
- 标题、前置条件、步骤动作和步骤预期必须能被执行人独立理解；禁止写入“蓝湖”或大小写不敏感的 `lanhu` 等外部设计工具名称及其设计稿节点、文件名或按钮依赖。需要表达依据时，改写为正式页面字段/控件基线、页面规则或当前页面实际显示内容。

## 3. 标题写法

### 3.1 推荐结构

标题围绕以下三个要素组织：

> 业务条件/场景 + 操作对象 + 可验证结果

推荐使用简洁的陈述句，不使用“测试……”“验证……”作为无信息量的开头。

### 3.2 写作要求

- 明确业务条件，例如“到期且待发货”。
- 明确页面、单据、行或字段等操作对象。
- 明确最终要验证的行为或结果，例如“展示可用发货入口”“字段可见并可回读”。
- 不把多个互不相关的结果堆叠在一个标题中。
- 避免使用模糊词：`正常`、`正确`、`相关信息`、`等`；如必须使用，应补充具体可观察表现。

### 3.3 示例

- 推荐：`到期且待发货行按业务键展示可用发货入口`
- 推荐：`进入发货执行页展示主要页面板块`
- 推荐：`发货单主信息字段可见并可回读`
- 不推荐：`测试发货功能`
- 不推荐：`验证页面是否正常`

## 4. 前置条件写法

### 4.1 内容要求

前置条件只描述执行用例前必须已经满足的条件，包括：

- 测试账号的权限条件；
- 页面访问条件；
- 目标业务数据及其关键状态；
- 与本场景直接相关的业务日期、数量或状态条件。

### 4.2 写作要求

- 使用可复现、可检查的状态描述，不写无法确认的泛化条件。
- 一条前置条件表达一个独立条件，使用无序列表。
- 只有确实需要时才列出多条条件，避免重复登录、菜单路径等操作步骤。
- 数据条件应尽量写出关键筛选值，例如计划发货日期、业务状态、实际可发数。
- 不写执行过程，不使用“点击”“查看”“输入”等操作动词作为前置条件主体。
- 不写账号密码明文，权限使用“具备相应权限的测试账号”表达。

### 4.3 示例

```md
**前置条件**:
- 测试环境已准备计划发货日期不晚于当前业务日期、状态为待发货且实际可发数大于0的授权发货单
```

或：

```md
**前置条件**:
- 具备页面访问权限；
- 存在目标发货单且状态允许操作
```

## 5. 步骤与预期写法

### 5.1 固定结构

```md
**步骤**:
1. 使用具备相应权限的测试账号登录系统
   - 预期：登录成功，进入系统门户或应用入口页
2. 在应用门户选择「种禽孵化管理系统」，展开「计划管理」并点击「雏苗发货」
   - 预期：进入「雏苗发货」列表页，页面标题或内容区显示「雏苗发货」
```

### 5.2 步骤写作要求

- 每一步只描述一个连续、可执行的用户动作或紧密动作组合。
- 登录步骤使用：`使用具备相应权限的测试账号登录系统`。
- 页面进入步骤明确应用、菜单层级和目标页面，例如：`在应用门户选择「种禽孵化管理系统」，展开「计划管理」并点击「雏苗发货」`。
- 操作对象使用页面实际显示名称，并使用「」标识菜单、按钮和页面名称。
- 查看、点击、选择等动作应明确目标对象，例如“目标发货单行的「发货」按钮”。
- 步骤按从登录、进入页面、定位目标数据到执行验证的顺序组织。
- 不在步骤中混入代码、定位器、接口调用或数据库操作。
- 禁止使用“执行本用例的单一业务操作”“执行相关操作”“进行处理”等无法复现的占位语。
- 每个动作至少写明操作对象和动作内容；涉及业务验证时，还应写明目标数据、条件、输入值、按钮或查询方式。
- 并发、幂等、回滚、权限和外部回传场景必须写出触发动作及结果回读对象，不能只写抽象业务结果。
- 同一套数据基线、同一动作或连续动作链、同一业务结果下，提交动作、结果回读和关联字段/公式校验可以放在同一个用例中，但必须拆成多个连续步骤；第一步只验证动作结果，后续步骤验证回读或关联一致性。步骤应明确通过什么页面、记录或业务键定位回读对象，不得只写“查看结果”或“进行核对”。
- 边界值期望必须同时写明输入值、校验结果、可操作控件状态和排除性提示；禁止使用“放行”“按规则通过”“正常提交”等无法直接观察的概括性表述。

### 5.3 预期写作要求

- 每个步骤必须有且只有一个紧随其后的 `- 预期：` 行。
- 当一个原预期包含“选项/字段展示”与“选择后查询或联动结果”等不同验证对象时，应拆成两个连续步骤：第一步验证展示内容，第二步执行选择或查询并验证结果。
- 预期描述对应动作完成后页面、数据或状态的可见变化，不把后续操作的结果写入当前步骤预期。
- 对空态、筛选无结果等场景，必须明确写出页面显示的空态文案、被排除的记录范围和仍应保留的字段/信息；禁止使用“无误显示”“不误显示”“保持不变”等无法准确判断的概括性表述。
- 当一个预期同时验证“没有显示什么”和“仍然保留什么”时，应分别写出具体对象，例如“页面不显示其他计划记录；发货单的基础信息仍显示原来的内容”。
- 优先使用“进入……页”“……可见”“……显示……”“……与授权数据一致”等可核验表达。
- 页面结果应包含页面名称或关键区域；数据结果应包含字段、值、状态或一致性要求。
- 一个预期包含多个并列验证点时，仅限这些验证点属于同一页面/同一数据块、同一业务结果和同一数据基线；例如表格列名整体、状态卡组成项、同一统计结果的纳入/排除范围可合并。
- 正向结果与用于排除等价错误结果的必要反向约束可以合并，但不得借此合并互斥状态、不同数据基线或不同业务结果。
- 独立业务结果、不同数据基线或可独立定级的验证点必须拆分步骤或用例；若多个验证点仍属于同一数据基线和同一业务结果，只拆分为连续步骤，不拆分为多个用例。
- 不以“应该”“大概”“无异常”等主观或不确定词作为核心结论。

### 5.4 推荐结果词汇

- `登录成功，进入……`
- `进入……列表页，页面标题或内容区显示……`
- `到达……页，……区域可见`
- `目标行展示可点击且未置灰的……入口`
- `字段可见且与授权数据一致`
- `页面显示……，且……状态符合条件`

## 6. 与结构化字段的对应关系

生成 YAML 时，按以下方式映射，不改变现有 Schema：

| 风格字段 | YAML 字段 | Markdown 字段 |
| --- | --- | --- |
| 标题 | `cases[].title` | `**标题**` |
| 前置条件 | `cases[].preconditions[]` | `**前置条件**` 下的列表 |
| 步骤动作 | `cases[].steps[].action` | 编号步骤 |
| 步骤预期 | `cases[].steps[].expected` | 步骤后的 `- 预期：` |

YAML 是用例明细事实源；Markdown 应由既有渲染流程派生并通过校验，不要维护与 YAML 不一致的第二份事实数据。

## 7. 生成前检查清单

- [ ] 标题包含业务场景、操作对象和可验证结果。
- [ ] 前置条件可复现，包含必要的权限和数据状态。
- [ ] 每个步骤都是可执行的用户动作。
- [ ] 每个步骤紧跟一条 `- 预期：`。
- [ ] 预期包含页面、字段、数据或状态等可核验结果。
- [ ] 并列断言属于同一业务目的、同一数据基线和同一业务结果；未按字段机械拆分。
- [ ] 统计、公式或整体布局的必要反向约束已与正向结果保持同一数据基线。
- [ ] 结果回读步骤明确记录、页面区域或业务键等定位对象，不使用“查看结果”“进行核对”等概括动作。
- [ ] 菜单、按钮、页面名称与项目术语一致，并保留「」标点。
- [ ] 标题、前置条件、步骤动作和步骤预期不包含“蓝湖”或大小写不敏感的 `lanhu`；不依赖设计稿节点、设计文件名或设计稿专属按钮名称。
- [ ] `cases[].title`、`preconditions[]`、`steps[].action` 和 `steps[].expected` 与 Markdown 内容逐条对应。

## 8. 规则文字专项检查

标题、前置条件、步骤和预期必须直接写出执行所需的业务规则。禁止使用“按已确认规则”“页面定义”“页面约定”“按规则”“正常显示”“保持一致”等无法让执行人判断结果的表述。应替换为具体字段、数值、公式、状态、文案或明确的 blocked 边界；例如：`实际可发等于0时显示0%`，而不是“按页面定义显示”。

如果业务规则确实尚未确认，必须在前置条件或预期中写明具体未确认对象，并明确本用例保持 `blocked`、不判定任一猜测结果；不得用占位短语掩盖缺失契约。

## 9. 占位步骤专项检查

生成前扫描：

- [ ] `steps[].action` 不包含“执行本用例的单一业务操作”“执行相关操作”“进行处理”等占位表达。
- [ ] 每个动作都能回答“对什么对象做什么动作”，并在需要时包含数据、条件、按钮或输入值。

生成后扫描：

- [ ] 对 YAML 和 Markdown 同时执行占位语精确搜索，结果为 0。
- [ ] 随机抽查或结构化比对每条用例的编号、标题、前置条件、动作和预期，确认 Markdown 由 YAML 派生且未产生漂移。
- [ ] 并发、重复提交、失败回滚、外部回传及权限场景均包含触发操作和可观察结果回读。
- [ ] 生成后扫描 YAML 与 Markdown 的业务字段，确认“蓝湖”和大小写不敏感的 `lanhu` 命中数均为 0。
