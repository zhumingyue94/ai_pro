# QA 公共项目契约

## 目的

本目录用于承载多个 QA 子项目共享的、可复核和可追溯的分阶段测试工作流。项目业务事实、业务适配和环境差异不得写入本公共契约。

## 平台应用与权限背景

### 平台入口与应用结构

- 用户登录后先进入 `/portal` 应用门户，再从应用列表进入目标系统。
- 种禽孵化管理系统、产业链生产排程系统、商品禽养殖管理系统等均为相互独立的应用。
- 进入具体应用后，才展示该应用所属的一级菜单、子菜单和业务页面。
- “基础设施”同样是独立应用，进入后可访问“系统管理”及其子菜单。

### 菜单层级示例

应用内菜单应按照实际层级描述，例如：

`种禽孵化管理系统 > 计划管理 > 雏苗发货`

### 页面导航方式

- 平台页面不使用面包屑展示页面层级，也不应将面包屑作为页面定位或测试断言依据。
- 点击应用内菜单后，目标业务页面会在页面框架内打开一个 Tab 页。
- 当前页面通过目标 Tab 已打开且处于选中状态进行确认。
- “应用 > 一级菜单 > 子菜单 > 页面”仅用于描述逻辑访问路径，不代表页面上会显示同名面包屑。

### 权限模型

角色管理用于配置用户在平台中的访问范围，通常包括：

- 应用权限：是否可以进入目标应用；
- 菜单权限：是否可以查看和使用应用内菜单；
- 接口权限：是否可以调用对应业务接口。

进行需求分析或生成测试用例时，应分别核对门户、应用、菜单和接口权限，避免将应用权限与应用内菜单权限混为一谈。测试用例的前置条件和步骤应依次描述进入应用门户、选择目标应用、点击应用内菜单，并以目标 Tab 已打开且处于选中状态确认页面已进入；不得编写“检查面包屑”的步骤或预期结果。具体项目的角色、权限和菜单事实以项目资料为准；暂未明确的内容标记为“待确认”。

## 阶段流转

需求输入 → 需求分析 → 测试计划 → 生成测试用例 → 用例评审 → 禅道同步 → 自动化测试（含缺陷报告）→ Bug 验证 → 回归测试

每个阶段只写本阶段产物，并通过相对路径引用上游结果。质量门禁采用 `report_only`：门禁未通过时必须保留失败原因，但不得阻断进入下游；上游产物缺失时不得伪造产物，应记录 `input_missing` 并继续编排。

## 公共资源边界

- 公共 Agent 资源位于 `.agents/`，公共 Schema 位于 `.agents/references/`，公共脚本位于 `scripts/`。
- 项目从项目根目录通过 `.agents/`、`.agents/references/`、`scripts/` 加载公共资源。
- 项目本地 `.agents/rules/` 只允许保存业务专属规则；不得复制公共 Rule、Skill、Schema 或脚本。
- 项目本地约定文件只有在存在实际业务差异时才保留，并且必须引用本文件而不是重复全文。

## 基本约定

- 所有文本文件使用 UTF-8 编码。
- 不编造具体业务模块、接口、页面、数据或执行结果；不确定内容使用占位符并标明待确认。
- 不提交真实账号、密码、令牌、Cookie、密钥、生产数据或其他敏感信息。
- 外部系统只允许通过明确授权的配置或交互式登录接入；凭据不得写入仓库。
- 每个阶段只写入本阶段定义的产物，跨阶段修改必须留下原因和来源说明。
- 需求、测试计划、用例、评审、同步、自动化、缺陷和回归之间应保留可追溯标识。
- “候选”“已生成”“静态检查通过”“远程执行通过”必须明确区分，不能互相替代。
- 任何执行结果必须包含执行时间、环境标识、范围和证据位置；没有证据时标记为“未验证”。
- `02_analysis` 至 `05_case_review` 属于设计与交付准备阶段；正式环境 URL、权限、测试数据和清理责任未就绪时，可记录为风险、依赖或后续执行准备项，不作为本阶段门禁、阻塞或失败依据。
- 页面清单与采集结果（`page.json`、`design.json`、`contract_status`、`evidence`、`capture_id`、截图、DOM 快照、是否已采集）在 `02_analysis` 至 `09_regression` 全部阶段只作普通参考；不得作为任何环节的门禁、阻塞、`blocked`、`input_missing`、`gate_reasons` 或 `gate_passed: false` 依据，也不得作为任何字段（含 `auto`、`type`、`priority`）的判断条件。用例评审不把页面清单或采集结果列为输入、维度或检查项；页面采集作业质量规则不影响本条。
- `06_zentao_sync` 及真实 UI 执行和后续执行阶段，涉及远程写入、业务提交或数据变更时，必须在执行前确认环境用途、授权、凭据、数据隔离和清理责任；未经确认不得执行写操作。
- 测试数据的创建、修改和清理必须记录责任边界；未经确认不得擅自恢复或删除用户数据。
- 仓库内所有 Python 函数（`def`，含模块级函数与类方法）必须提供 docstring，说明函数作用；无 docstring 的函数视为未达标。
- Playwright 打开的浏览器必须始终使用可视模式，固定设置 `headless=False`。
- 禁止默认切换为无头模式；如果环境无法启动可视浏览器，必须将任务标记为阻塞并记录原因，不得用无头模式替代。
- 当任务明确使用 `webapp-testing` Skill 时，以该 Skill 自带的浏览器工具、启动方式、交互方式和执行规则为准，不强制套用其他默认浏览器工具约定。

## 阶段交接

1. `01_requirements` 接收原始需求和需求来源，不计入 Agent 阶段。
2. `02_analysis` 输出结构化需求分析和范围边界。
3. `03_test_plan` 输出测试范围、策略、风险、环境、数据和套件规划。
4. `04_testcases` 输出可执行测试用例。
5. `05_case_review` 输出用例评审、筛选和待同步清单。
6. `06_zentao_sync` 记录经授权的同步操作、回读证据并生成项目根目录唯一 `module_case_map.json`。
7. `07_ui_automation` 执行自动化测试，并在同一 RUN 内生成缺陷候选/报告。
8. `08_bug_verification` 验证自动化阶段生成的产品缺陷报告。
9. `09_regression` 根据代码 diff 分析影响模块和用例，执行受影响用例并生成回归报告。

## 变更与验证

- 新增 Rule、Skill、Schema 或公共脚本前，先说明适用范围、输入、输出和副作用。
- 运行脚本前检查其作用范围、配置来源和数据生命周期。
- 验证至少覆盖：文件结构、格式/schema、关键脚本静态检查；需要真实系统或浏览器时，单独声明尚未完成的外部验证。
- 发现不一致时保留原始证据，不用“通过”掩盖缺失、失败或未执行。

## 阶段门禁

- 用例评审等质量门禁只用于记录 `gate_passed` 和 `gate_reasons`，不作为阶段流转条件。
- `gate_passed: false` 时继续进入下游，并在 Handoff/Pipeline Summary 中列出具体失败原因。
- 用例生成阶段只产生 YAML/Markdown，不直接产生禅道 CSV。
- UI 执行完成后必须记录分类、证据和缺陷报告；不自动创建远程缺陷。

## 门禁执行策略

- 默认 `workflow.gate_policy` 为 `report_only`。
- `02_analysis` 至 `05_case_review` 只对输入完整性、需求与计划追溯、测试设计质量、范围和人工可判定性设置门禁；正式环境 URL、权限、测试数据和清理责任缺失只能记录为风险、依赖或后续执行准备项，不得生成 `blocked`、`input_missing` 或 `gate_reasons`，除非它们本身是该阶段明确要求的上游输入。
- `gate_passed` 必须如实记录，不得为了推进流程而改成 `true`；取消上述前置门禁不等于可以编造环境、权限、数据或执行结果。
- `06_zentao_sync` 及真实 UI 执行和后续执行阶段，凭据、显式执行参数、远程写入授权、浏览器和环境可用性、数据隔离及清理责任仍是安全执行条件；不满足时只记录 `not_executed`/`blocked` 原因，不伪造远程成功或真实执行证据。
- `06_zentao_sync` 及真实 UI 执行阶段不得以页面清单缺失、未采集、缺少已确认 locator 或证据不完整作为 `not_executed`/`blocked` 的理由；定位与执行可行性依据真实 DOM 与运行时探索独立判断。
- Pipeline Summary 使用 `completed_with_gate_issues` 表示“已继续但存在设计门禁问题”；真实执行安全条件不满足时记录 `not_executed`/`blocked`，不得与前置阶段质量门禁混淆。

## 产物要求

每次阶段交接至少记录：输入路径、输出路径、处理时间、门禁结论、未解决问题、风险和下一步。禅道同步还必须记录注册表路径、来源哈希和回读状态；自动化测试还必须记录 RUN、结果报告和缺陷报告路径。

敏感配置只从环境变量或本机安全存储读取；仓库内配置只保留非敏感占位字段。

每次 Agent 任务结束前，必须清理任务过程中生成的中间产物，包括临时 `.py`、`.ps1`、`.js` 文件、`__pycache__`、`.pytest_cache`、临时日志、临时报告和缓存文件。

任务目录只保留最终交付物、必要的执行证据和用户原有文件。

不得删除用户已有的历史产物、输入文件、评审记录或明确要求保留的证据；若中间文件因证据需要保留，必须在交接记录中说明用途。

清理完成后必须复查目录，确认无临时脚本和缓存残留。





## 🔴 Mandatory Rules（强制性规则）

以下规则是**必须遵守**的，不得以任何理由跳过或忽略。


### 规则 1：命令执行必须优先使用 RTK

对于输出量大的命令，不要直接使用原命令，必须优先重写为对应的 RTK 命令。只有在符合“允许回退到原命令”的条件时，才可以跳过 RTK。如果最终决定回退到原命令，你也应尽可能缩小输出范围，避免产生过大的输出。

**适用命令类型（包括但不限于）**：
- `git status`、`git diff`、`git log`
- `grep -r`、`find`、`ls -la`（在大型目录下）
- `cat` 或 `less` 查看大文件
- `npm list`、`pip list`、`go mod graph`
- `ps aux`、`netstat`、`lsof`
- 任何可能输出超过 50 行的命令

**❌ 错误示例**：
```bash
git status
```

**✅ 正确示例**：
```bash
rtk git status
```

**例外情况**：
- 输出量很小（< 10 行）且明确已知的命令可以不加 `rtk`
- 需要实时交互的命令（如 `vim`、`top`、`watch`）不适合使用 `rtk`


### 规则 2：RTK 使用优先级

#### 必须优先使用 RTK

- 文件读取
- 搜索输出
- git status / diff / logs
- 测试输出
- 构建 / lint 输出
- docker / kubectl logs

#### 建议使用 RTK

- 包列表查询
- 依赖分析
- 包管理器的查询类输出
- 其他已知会产生大量输出的命令

#### 可以直接使用原命令

- pwd
- echo
- 输出非常短的命令
- 有严格输出格式要求，且 RTK 可能改变其格式的命令
